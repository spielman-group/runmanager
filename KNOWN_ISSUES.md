# Known issues

- `__main__.py`, `RunManager.offer_shot` and `take_default_shot`: a default shot that cannot be made is attempted again on every BLACS request, about once a second while BLACS has no local override shot. A missing default labscript file makes `offer_shot` raise, and the exchange writes a red line each time; a default script that fails to compile is compiled again each time, with its traceback, keeping the compiler busy ahead of Engage's shots. Possible fix, about 49 lines: remember the failure while labscript-utils' `FileWatcher`, hashing, watches the script and the active globals files from the attempt's start. Any event, or a change of policy, script or group activation, releases it, and a generation tag drops a superseded attempt's result. Stop the watcher from another thread, since its callback holds its lock.
- `__main__.py`, `RunManager.on_close_event`: closing while a default shot is being prepared leaves its file in the shot folder, since the preparation hands the shot over after the close has deleted any ready one. Deferred: waiting for it would hold the close on a compile, and deadlock on the preparation's `inmain` read of the active groups.
- `docs/source/conf.py`: `autodoc_mock_imports = ['labscript_utils']` mocks the base class of `RunmanagerClient`, so `runmanager.remote` fails to import in the docs build (`RunmanagerClient.instance()` is missing), and the API reference has no page for the remote client users import.
- `expander.py`, `value_expression`: a scanned global is frozen for the compile as text that does not always evaluate back to its value. An empty `(0, 3)` array comes back with shape `(0,)`, a structured array's dtype is not understood, so its shot fails to compile, and nan and inf are written as `nan` and `inf`, which only pylab's names define.
- `compiler.py`, `get_queue_compile_globals`, called by `__main__.py`'s `prepare_queue_shot`: the compile evaluates every global again for each shot, with each scanned global's value in that shot, where Engage evaluated them once with its whole list. A global that is not scanned and uses a scanned one then differs from Engage: with an outer `x = np.array([1, 2])`, `y = 2*x` is `[2, 4]` at Engage but 2 and 4 in the files, and `n = len(x)` engages, then fails to compile.
- `compiler.py`, `get_queue_compile_globals`: a shot file's `/globals` group records each scanned global as its frozen text with no expansion, in place of the user's expression: `np.int64(1)`, not `np.array([1, 2])` with `outer`. lyse's `Run.get_globals_raw` and `Run.get_globals_expansion` read that record.
- `evaluator.py`, `_evaluate_globals`: a global whose expression binds another global's name with `:=`, as `y = (x := 1)` beside a global `x`, overwrites `x` in the shared namespace for the globals evaluated after it. Left by Ian's decision.
- `evaluator.py`, `_global_references`: an expression with over a thousand nested lambdas exceeds the recursion limit, and the RecursionError escapes `evaluate_globals` even with `raise_exceptions=False`. Upstream's code; no reasonable global nests so deep.
- `evaluator.py`, `_evaluate_globals`: an expression too large for `compile`, such as 100,000 additions, raises a RecursionError that escapes `evaluate_globals` even with `raise_exceptions=False`, since only a SyntaxError is held. Upstream's code; no reasonable global is so large.
